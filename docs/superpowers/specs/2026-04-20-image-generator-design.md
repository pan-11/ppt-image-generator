# 本地图片生成工具设计文档

## 1. 目标

构建一个仅在本机运行的图片生成网站，服务单一使用者，围绕 ToAPIs 网关实现高效批量生图。

该工具需要满足以下核心目标：

- 支持一次性提交多条提示词任务，默认允许单批提交至少 20 条任务
- 支持固定并发池执行，默认并发数为 5，任一任务结束后自动补位下一条等待任务
- 支持文生图与带参考图的图生图/编辑模式
- 支持每行任务独立设置参数，而不是整批共用单一参数
- 支持本地保存历史记录，并允许删除单图或整个批次
- 支持单图下载、选中下载、整批 ZIP 下载
- 将 API Key 保留在本地后端，避免暴露到浏览器

## 2. 非目标

第一版不包含以下范围：

- 用户注册、登录、权限系统
- 多用户协作或多租户隔离
- 云端同步历史记录
- 远程服务器部署
- 自动化工作流编排
- 高级模板系统或复杂素材库
- 面向手机端的专门适配

## 3. 运行场景

工具运行在用户本机，通过浏览器访问本地地址使用。前端页面仅作为界面层，本地后端负责与 ToAPIs 通信、保存数据和管理文件。

预期使用方式如下：

1. 用户打开本地网页
2. 在表格中粘贴或编辑多条提示词任务
3. 为每一行分别设置模型、尺寸、张数、参考图模式和参考图文件
4. 一次性提交整批任务
5. 后端按并发上限逐步调度执行
6. 图片生成成功后自动保存到本地数据目录
7. 用户在当前结果区或历史记录页查看、筛选、下载、删除

## 4. 系统架构

系统采用三层架构：

- 前端 Web 界面
- 本地后端服务
- 本地存储层

### 4.1 前端职责

前端负责：

- 展示批量任务编辑器
- 管理默认参数与行级覆盖
- 触发任务提交、暂停、继续、重试、删除、下载操作
- 实时展示任务状态、缩略图、失败原因、批次进度
- 浏览历史记录并进行筛选

前端不直接调用 ToAPIs，不接触真实 API Key。

### 4.2 后端职责

后端负责：

- 读取本地配置和 API Key
- 接收前端上传的参考图文件
- 将参考图上传到 ToAPIs 并缓存远程 URL
- 调用 ToAPIs 的图片生成接口创建远程任务
- 轮询远程任务状态
- 在任务成功后立即下载结果图到本地
- 维护本地任务队列、并发池和重试机制
- 写入数据库记录和本地日志
- 生成单图下载流、选中下载流和批次 ZIP 下载流

### 4.3 存储职责

存储层由两部分组成：

- 本地数据库：保存任务、批次、图片、参考图、日志和配置索引
- 本地应用数据目录：保存生成图片、参考图副本、ZIP 临时文件

该设计确保即使 ToAPIs 返回的图片 URL 在 24 小时后过期，本地历史记录仍然可用。

## 5. ToAPIs 集成约束

根据 ToAPIs 文档，设计需要遵守以下约束：

- 鉴权使用 `Bearer` API Key，Base URL 为 `https://toapis.com/v1`
- 图片生成通过 `POST /images/generations` 发起
- 图片生成是异步任务，需要轮询任务状态
- 任务状态通过 `GET /images/generations/{task_id}` 查询
- 结果图片 URL 有时效性，后端必须在完成后尽快下载到本地
- 参考图需要先通过上传接口获取远程 URL，再在生成请求中通过 `image_urls` 传入
- 模型能力存在差异，部分模型不支持相同的张数、尺寸或图生图模式

因此系统必须维护一份模型能力配置表，用于驱动前后端参数校验。

## 6. 页面设计

第一版提供三个核心页面或区块。

### 6.1 任务编辑区

任务编辑区是主工作台，核心是表格编辑器。每一行表示一个待执行任务。

建议字段如下：

- 启用
- 提示词
- 模型
- 尺寸
- 张数
- 参考图模式
- 参考图文件
- 状态
- 结果数
- 操作

支持的行级操作：

- 新增一行
- 复制一行
- 删除一行
- 批量粘贴多行提示词
- 清空已完成
- 清空失败项

### 6.2 运行监控区

运行监控区显示整个批次的执行情况，包括：

- 批次名称或生成时间
- 总任务数
- 等待中数量
- 运行中数量
- 成功数量
- 失败数量
- 当前并发数
- 暂停按钮
- 继续按钮
- 重试失败项按钮

### 6.3 历史与结果区

历史区按批次展示历史任务。每个批次包含：

- 批次创建时间
- 任务总数
- 成功数
- 失败数
- 结果缩略图列表
- 关键词搜索
- 按模型筛选
- 按日期筛选

每张结果图需展示：

- 缩略图
- 原始提示词
- 模型
- 尺寸
- 生成时间
- 下载按钮
- 删除按钮

## 7. 批量编辑与默认值策略

为了兼顾高效批量录入与逐行独立参数配置，界面采用“全局默认值 + 行级覆盖”的方式。

### 7.1 全局默认值

表格上方提供默认设置栏，至少包含：

- 默认模型
- 默认尺寸
- 默认张数
- 默认参考图模式
- 默认全局参考图

新建行时自动继承这些值。

### 7.2 行级覆盖

每一行都可以覆盖默认值，互不影响。用户可以在不改变整批设置的前提下，为少数任务设置不同模型、尺寸、张数或参考图。

### 7.3 参考图模式

参考图模式定义为三个选项：

- 无参考图
- 使用本行参考图
- 使用全局参考图

该设计可同时支持：

- 纯文生图
- 整批共用一张参考图
- 少数行使用自己的参考图

## 8. 任务模型与状态机

### 8.1 批次

一次点击“开始生成”所提交的全部任务构成一个批次。批次是历史记录和 ZIP 下载的主要管理单位。

### 8.2 单任务

每一行是一条独立任务。任务之间互不阻塞，某一条失败不影响其他条继续执行。

### 8.3 状态定义

单任务状态建议定义为：

- `draft`：草稿，尚未提交
- `queued`：已进入本地等待队列
- `submitting`：正在向 ToAPIs 提交
- `remote_queued`：远程排队中
- `remote_in_progress`：远程生成中
- `downloading`：正在下载结果图到本地
- `completed`：已成功完成并落盘
- `failed`：已失败
- `paused`：被用户暂停，等待继续

前端默认展示更友好的中文状态：

- 等待中
- 运行中
- 下载中
- 成功
- 失败
- 已暂停

## 9. 调度与并发策略

系统使用固定并发池进行调度。

### 9.1 核心规则

- 单批支持一次性提交至少 20 条任务
- 默认最大运行并发数为 5
- 当运行中的任务少于 5 条时，调度器自动从等待队列中补位
- 任一任务完成、失败或终止后，立即检查是否需要补位下一条
- 用户无需手动分批点击

### 9.2 队列结构

建议维护两个核心集合：

- 等待队列
- 运行中集合

调度器循环执行以下逻辑：

1. 检查当前运行中数量
2. 若小于并发上限，则从等待队列取下一条
3. 启动提交和轮询流程
4. 在任务进入最终状态后释放并发槽位
5. 自动补位新任务

### 9.3 暂停与继续

暂停行为定义为：

- 不再启动新的等待任务
- 已经在远程执行中的任务继续轮询直至得到最终结果

继续行为定义为：

- 重新允许调度器从等待队列取任务补位

## 10. 参考图处理流程

参考图处理必须经过本地后端。

流程如下：

1. 用户在前端选择本地图片文件
2. 前端将文件上传到本地后端
3. 后端保存参考图本地副本
4. 后端将图片上传到 ToAPIs 上传接口
5. 后端获得远程 URL
6. 生成请求时将 URL 放入 `image_urls`

### 10.1 参考图缓存

后端需要实现批次级缓存：

- 同一张本地文件在同一批次内只上传一次
- 多行共用同一参考图时直接复用已获取的远程 URL

数据库中需要记录：

- 本地参考图路径
- 文件哈希或唯一标识
- 远程 URL
- 首次上传时间
- 所属批次

## 11. 图片下载与本地保存

### 11.1 保存原则

远程任务成功后，后端必须立即将结果图下载到本地应用数据目录，而不是只保存远程 URL。

### 11.2 本地保存结构

建议保存为按批次组织的目录结构，例如：

`app-data/batches/<batch-id>/images/...`

参考图建议保存为：

`app-data/batches/<batch-id>/references/...`

ZIP 临时文件建议保存为：

`app-data/tmp/zips/...`

### 11.3 文件命名

图片文件名应具备可读性和稳定性，推荐包含：

- 生成日期
- 批次编号
- 行编号
- 结果序号

例如：

`2026-04-20_batch-003_row-12_1.png`

## 12. 下载能力

系统需要支持三种下载方式：

- 下载单张图片
- 下载选中的多张图片
- 下载整个批次的 ZIP 包

其中：

- 单张下载直接返回本地文件
- 多张选中下载可以临时打包 ZIP
- 批次下载默认生成 ZIP

ZIP 包内文件命名需要与数据库索引一致，便于用户在导出后仍可追溯来源。

## 13. 历史记录与删除策略

### 13.1 历史结构

历史记录按“批次 -> 任务 -> 图片结果”三层组织。

### 13.2 删除单图

删除单图时需要：

- 删除图片记录
- 删除本地图片文件
- 保留任务本身，但更新结果数量

### 13.3 删除整批

删除整批时需要：

- 删除批次记录
- 删除该批次下所有任务记录
- 删除所有结果图记录
- 删除该批次的图片目录和参考图目录

### 13.4 删除确认

删除动作需要明确确认：

- 删除单图时显示基础确认框
- 删除整批时显示更强提示，明确即将删除的任务数和图片数

## 14. 参数校验策略

参数校验必须在前后端都存在。

### 14.1 前端校验

前端负责尽早提示用户，包括：

- 提示词不能为空
- 模型必选
- 尺寸必须是模型支持范围内的值
- 张数必须在模型支持范围内
- 选择本行参考图时必须上传图片
- 选择全局参考图时必须已配置全局图片

### 14.2 后端校验

后端负责最终兜底，包括：

- 再次验证参数组合是否合法
- 验证所选模型是否支持参考图模式
- 验证张数和尺寸是否超出模型能力表限制

如果后端发现参数错误，直接将任务置为失败，并记录明确原因，不进入自动重试。

## 15. 失败处理与重试策略

### 15.1 失败分类

失败至少分为三类：

- 提交失败
- 生成失败
- 下载失败

### 15.2 自动重试规则

以下情况允许自动重试：

- 网络超时
- 短暂连接错误
- `429` 限流
- 下载结果图时的短暂网络异常

以下情况不自动重试：

- 参数错误
- 模型不支持当前配置
- 明确的鉴权错误

### 15.3 用户重试操作

前端需支持：

- 重试失败项
- 仅重跑选中项

重跑时应保留原有提示词和参数，方便用户快速再次提交。

## 16. 日志与可观测性

后端需要记录本地日志，至少包含：

- 批次 ID
- 本地任务 ID
- 远程任务 ID
- 请求时间
- 响应状态
- 状态变化
- 失败原因
- 下载完成时间

日志用于排查以下问题：

- 某条任务为什么失败
- 某张图片为什么未成功落盘
- 是否发生了限流或远程接口异常

## 17. 页面刷新与恢复

由于后端在本地独立运行，页面刷新后应能恢复当前状态。

恢复逻辑如下：

- 前端启动时读取当前活跃批次和任务状态
- 如果任务仍在运行，前端继续订阅或轮询本地后端状态
- 如果任务已完成，前端直接展示已落盘结果

该设计确保用户误刷新页面后不会丢失运行进度。

## 19. 技术边界与实现原则

第一版实现需要遵守以下原则：

- API Key 只保存在后端配置中
- 前端不直接请求 ToAPIs
- 所有远程结果图必须落地到本地
- 并发调度必须严格受控，默认最大并发数为 5
- 删除记录时同步清理本地文件，避免孤儿文件堆积
- 模型差异通过配置表驱动，不将规则硬编码分散到多个界面逻辑中

## 20. 验收标准

当以下条件全部满足时，可认为第一版达标：

- 用户可以一次性粘贴并提交至少 20 条任务
- 系统同时最多运行 5 条任务，并在任务结束后自动补位
- 每一行任务都可以独立设置参数
- 用户可以使用无参考图、本行参考图、全局参考图三种模式
- 任务完成后图片可在本地历史记录中长期查看
- 支持单图下载、选中下载和整批 ZIP 下载
- 用户可以删除单图和整批历史，且文件同步被清理
- 页面刷新后仍能恢复任务状态或结果
- 常见网络波动不会导致整批任务中断
